如果附有截图，它只是构图、细节密度和角色像素风的参考；不要复刻截图中的编辑器 UI。每批建议 30–50 个创建对象、总计不超过 120 个操作，为材质、变换和设置预留空间。请先保存一次主要建筑，再继续细节，最后再保存完整版本，不能只在最后一次保存。

执行边界非常明确：只使用 h3d MCP 工具。不要创建另一个 Three.js/HTML/Vite 项目，不要使用终端、文件系统、浏览器自动化、外部连接器，不要修改编辑器源码。所有建筑、角色、材质、脚本都属于当前 Astral 场景。脚本可以使用编辑器提供的 THREE、scene、timer 等上下文；可以在场景脚本内部用 CanvasTexture 生成像素图集，但不能创建网页、DOM UI 或替代整个编辑器。禁止把全部建筑藏在一个运行时生成脚本中：静态建筑和可编辑物体必须通过 scene_batch 实际创建、分组和赋材质，保存后在编辑视口也能看到完整场景。

先读取 h3d_help / h3d_capabilities，理解真实几何、材质、脚本事件、动画、保存和截图契约。每次写入先读取最新 scene_status，携带 sessionId、sceneId、documentEpoch、expectedRevision 和新的 operationId。每批不超过 200 个操作；使用批内 ref 和批后 UUID。可用 InstancedMesh 高效制作重复石块、屋瓦、木条、叶片和栅栏。按地形/本殿/鸟居与庭院/植被/生活设施/角色/动效建立命名清晰的层级。当前专用测试项目可以正常修改，完成后必须显式保存；不能只留下未保存的内存场景。

场景要求：

1. 完整正方形底座，所有主要元素搭建在底座范围内。底座清晰分成石砌侧面、木制夹层和地面，边缘轻微圆角；石砌侧面要能辨认出单块石头与接缝。构图紧凑而有前后层次，前方开阔参道和庭院较低，神社主体在后方偏中央、台基稍高。第三人称斜俯视完整小景观，像可自由拖拽、旋转、缩放观看的精致收藏模型。背景简单、柔和，无街景，无 UI、标题、按钮或网页装饰。

2. 整体三渲二、日式二次元动画风格，干净材质、明确轮廓、柔和但有层次的色彩。用实际 MeshToonMaterial 或合适的自定义 GLSL、柔和阴影和少量克制的描边表现，避免写实金属反光或高饱和塑料感。应呈现宁静、灵动、幻想乡的氛围。至少有一种实际可编译、会显示的自定义 GLSL 材质，可用于手水舍水面或微弱灵性效果，其余主要建筑使用内置受光材质。方向光与环境/补光要兼顾正面和侧面，保持深色屋檐下仍能看见结构。

3. 神社本殿红白配色，黑灰或深色屋顶、宽大出檐，明显的坡屋面和檐口层次；不要用简单平盒子代替屋顶。包括正面台阶、台基、木地板、神社门扉、立柱与横梁、栏杆、屋檐下结构、赛钱箱（可见格栅/投币口）、注连绳与白色折纸纸垂、神社铃和木制铃绳。外部即能看出完整神社，而非空壳。侧面有木制墙板、纸拉门/侧窗、储物箱、木桶、祭典灯笼、简化社务所入口等生活细节。神社侧边附有小屋/仓库/社务所外部结构。建筑前平台开阔但不空泛。

4. 庭院包含神社前鸟居（有辨识度的朱红双柱、上下横梁、微翘顶梁）、石板参道、石阶、成对石灯笼、树木、灌木、石块、围栏、手水舍或简化净手区域、告示牌、绘马架、御神签架、扫帚/清扫工具、边缘小路，以及角落的落叶/花瓣。参道略有磨损和间距变化；植被成簇，庭院整洁但有生活感。绘马是可见的小木牌，御神签是白纸结，设施形态要互相区别。不要用同一种方块代替所有设施。可安排一棵有特色的樱花树或秋叶树，配低矮灌木与草簇，不要遮住本殿正面和灵梦。

5. 适度基础动效：树叶/草簇轻摇、绘马与纸垂轻晃、铃绳微摆、少量花瓣或落叶缓慢飘动、薄云缓慢移动、灯笼微弱闪烁、缓慢的光照变化。微小光点/灵气可有但非常克制。整体仍像精致静态模型，禁止夸张闪烁、剧烈摆动或满屏粒子。所有动效用编辑器的脚本或动画功能，使用文档列出的真实事件（beforeAnimation(delta) 接收秒数数值，变更后按需 render()），不要假设不存在的 update 生命周期。

6. 庭院前方加入 Q 版二维像素风博丽灵梦：深棕头发、巨大红色蝴蝶结、红白巫女服、白色袖套和红鞋，手持扫帚。像素轮廓用柔和深棕而非生硬纯黑，鲜艳程度适度降低，与三渲二场景统一。角色要清晰可辨认，不能只是几个色块的简略火柴人，也不能用 3D 胶囊/球体代替二维像素角色。

7. 灵梦使用受场景光照的二维 Mesh 面片和透明像素图集/立牌，NearestFilter 保持像素边界；透明区域不能显示矩形底板。可使用内嵌 data:image 的静态像素图/图集，或在场景脚本中根据明确像素数据生成图集。编辑状态也必须有可辨认的静态角色图像，运行后切换一组低帧率动作帧（约 6–8 fps），表现扫帚挥动、袖套、裙摆和蝴蝶结轻微变化。使用真正的 UV / texture offset / frame 变化，而非只把整个平面左右旋转来假装逐帧动画。设置合适 alphaTest、双面和阴影；实际透明轮廓接受光照并投射柔和阴影，同时配一个柔和贴地接触阴影。

8. 灵梦不能一直固定在一个位置。动作状态机：低帧率扫地几轮 → 轻微停顿和起跳预备（压低重心）→ 在庭院小范围内跳向新的空地 → 腾空抛物线 → 落地缓冲 → 继续扫地。约 6–10 秒完成一次换位，使测试期间能观察到多次完整周期。选择互不重叠的落脚点并避开台阶、建筑、灯笼等障碍；脚底贴合当地地面/石板高度，不能穿地或持续悬空。跳跃期间影子留在地面，随高度增加变大、变淡；落地后恢复。几轮后在停顿阶段改变扫地方向，左右交替。加入极轻微呼吸、重心转移、裙摆/蝴蝶结律动，不要完全静止，也不要夸张弹跳。

9. 扫帚能推动附近的几片落叶/花瓣，叶片应在地面上可见并有位移，不是纯文字声明。角色换位后继续处理附近落叶；另有少量缓慢飘动的叶片/花瓣。避免叶片无限堆积或移出底座。

便于真实验收的对象命名：角色位移根 Group 必须名为 Reimu；受光像素平面名为 ReimuSprite；独立的贴地接触阴影名为 ReimuShadow（不能作为随角色高度移动的子节点）；至少几片可运动叶片命名为 FallingLeaf_01、FallingLeaf_02 等。脚本可以给 Reimu.userData 记录 phase、cycle、facing，给 ReimuSprite.userData.currentFrame 记录真实帧索引，辅助诊断，但这些值必须反映实际场景变化。ReimuShadow 必须使用实际会变化的 material.opacity 与 object.scale，影子不能跟随角色一起升空。

创作与验证流程：
- 先建立完整构图及建筑，再丰富设施/植被/像素角色，最后加入脚本和材质动效。
- 用 viewport capture 反复检查外观，调整相机、比例、遮挡、配色与光照。取完整微缩场景的 3/4 视角，底座四边可读，神社正面与庭院角色同时看得清，不要把相机设为角色第一人称。
- 真正启动 Play，轮询直到 running，读取 diagnostics，至少观察一个完整扫地→跳跃→落地周期并捕获运行视口；如有脚本/材质错误，停下修复后重跑。运行截图应没有编辑器辅助线、网格或 UI。
- 运行场景可在 loaded 事件中设置 window.viewer.modules.viewHelper.hidden = false 来隐藏已有的方向立方体（这个现有接口的 false 表示隐藏）；保留 controls 以便用户旋转、拖动和缩放。不要创建新的 DOM 界面。
- 最后停止 Play，让作者场景保持干净且脚本仍保存；显式保存，确认 sceneVersion 增长、dirty 为 false。不要删除项目，留给用户查看。报告实际创建的主要层级、对象/实例规模、脚本/材质、保存结果，以及任何未实现的要求，不要把计划说成已完成。
